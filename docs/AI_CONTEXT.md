# Mechanic — контекст проєкту для ШІ, що готує промти

> Документ для ШІ (Claude у браузері), який формує завдання для ШІ-агента
> (Claude Code), що працює безпосередньо в репозиторії. Агент бачить увесь код,
> може запускати команди, тести, міграції. Тому промт має описувати **що і навіщо**,
> а не переписувати код. Актуально на 2026-10-23, коміт `30bcfcf`.

---

## 1. Що це

**«Журнал технічного обслуговування обладнання»** — внутрішній вебзастосунок для
механіка підготовчої дільниці №2 виробництва. Замінює паперові графіки ППР
(планово-попереджувального ремонту) і журнали ТО.

Користувачі: 1–2 людини (механік, керівництво). Інтерфейс повністю українською.
Головний користувач — Валентин (ім'я зараз захардкоджене в шапці).

Що робить система:
- веде перелік обладнання (машин), їх ТТХ і склад запчастин;
- планує роботи ТО/ремонтів на дати → місячний і річний графіки;
- фіксує фактично виконані роботи (журнал) і витрачені запчастини;
- автоматично відмічає план виконаним, коли до нього прив'язано запис журналу;
- показує прострочені плани, архів за роками/місяцями;
- рахує аналітику витрати запчастин по машині (з урахуванням аналогів/комплектів);
- друкує графіки, справу машини, перелік запчастин.

## 2. Стек

- Python 3 (локально 3.14), **Django 5.2.15**, SQLite, Django Templates
- Bootstrap 5.3 через CDN (власних static-файлів немає)
- `python-dotenv` — змінні з `.env`: `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `PORT`
- Автотестів немає. Перевірка: `python manage.py check`, `makemigrations --check`

  зовнішньому порту з різними URL-префіксами; Mechanic — під `/mechanic/` (див. §9).

## 5. Модель даних (`maintenance/models.py`)

| Модель | Суть | Ключові поля / правила |
|---|---|---|
| `Machine` | Обладнання | name, technological_number, inventory_number, brand, location, length, height, description, **is_active** |
| `MachineSpec` | ТТХ машини (OneToOne) | описи ЩЗТО, ТО-1, ТО-2, ТО-3 |
| `Person` | Дійові особи | full_name, position (choices: головний інженер, нач. підготовчої дільниці, механік, слюсар, інше), **is_active** |
| `Part` | Довідник запчастин/матеріалів | name, unit, description; дублікат = однакові name+unit+description без урахування регістру |
| `MachinePart` | Склад запчастин машини | machine, part, quantity; unique (machine, part) |
| `PartAnalyticalMapping` | Аналог/комплект | source_part → target_part × quantity_factor; без самопосилань і циклів A↔B |
| `MaintenanceType` | Вид робіт | code: `ТО-1`, `ТО-2`, `ТО-3`, `КР`, `СР`, `ПР` (для планів) + `Ремонт` (лише для журналу, створюється автоматично) |
| `MaintenancePlan` | Планова робота | machine, maintenance_type, planned_date, status, note |
| `MaintenanceLog` | Факт виконання | machine, maintenance_type, performed_date, work_description, responsible_person, executor, related_plan (nullable) |
| `MaintenanceLogPartUsage` | Витрата запчастин у роботі | maintenance_log, part, quantity; unique (log, part) |

Статуси плану: `planned`, `done`, `cancelled` зберігаються в БД.
**`overdue` (прострочено) обчислюється на льоту** у `get_effective_plan_status()`:
не done/cancelled і `planned_date < today`.

## 6. Ключова бізнес-логіка (`maintenance/views.py`)

- **Головна `/`** = місячний план-графік: рядки — машини, колонки — дні місяця.
  Клітинки кольорові за статусом. Клік по порожній клітинці → створити план;
  по заповненій → «Виконати» (форма журналу з прив'язкою до плану) або «Скасувати».
  Машини відсортовані за першим днем із планами. Фільтри: місяць, рік, машина, дата.
  Будується в `build_monthly_schedule_context()` — спільно для головної, архіву і друку.
- **План ↔ факт**: `sync_maintenance_log_plan()` — запис журналу з `related_plan`
  переводить план у `done`; при перев'язці на інший план старий повертається в `planned`.
  Вид ТО запису має збігатися з видом ТО плану.
- **Формування місяця** (`monthly_schedule_transfer`, `generate_monthly_plans`):
  копіює плани з місяця-джерела в цільовий без дублікатів; якщо днів менше —
  дата зсувається на останній день.
- **Масове створення планів** — formset `maintenance_plan_bulk_create`.
- **Річний графік ППР** — машини × 12 місяців.
- **Архів** — не окремі таблиці, а той самий графік у режимі лише для читання
  (показує й неактивні машини з історією за той місяць).
- **Справа машини** — історія робіт + витрачені запчастини; **ТТХ** — спецификація + склад запчастин.
- **Аналітика машини** — встановлена кількість запчастин vs фактично витрачена,
  витрата аналогів перераховується через `PartAnalyticalMapping`.
- **Друк**: місячний, річний графіки, справа машини, перелік запчастин.

## 7. Конвенції коду (агент дотримується їх)

- Лише **function-based views**; контекст через `build_context(page_title, ...)`,
  для друку — `build_print_context(...)`.
- Повернення назад: параметр `?next=`, перевіряється `get_safe_next_url()`.
- Усі URL у шаблонах — через `{% url %}`, у Python — `reverse()`/`redirect("ім'я")`.
  Жорстко прописаних шляхів немає.
- Форми успадковують `BootstrapMixin` (додає класи Bootstrap).
- **М'яке видалення**: `Machine` і `Person` деактивуються (`is_active=False`), не видаляються.
  Фізично видалити можна лише неактивну машину без жодних пов'язаних записів.
  Запчастину — лише якщо вона ніде не використовується.
- Списки вибору у формах показують лише активних осіб/машини.
- Повідомлення користувачу — `django.contrib.messages`, українською.
- Усі тексти UI, verbose_name, повідомлення — українською.
- Коміти — українською, у стилі `feat: …`, `fix: …`, `зміни: …`.

## 9. Поточне відкрите завдання: URL-префікс `/mechanic/` за Caddy

Агент проаналізував код і запропонував (ще **не реалізовано**, чекає підтвердження):
- **Не** `FORCE_SCRIPT_NAME`, а монтування всіх маршрутів через
  `path(f"{APP_URL_PREFIX}/", include(...))` в одному місці `urls.py`;
  з порожнім `APP_URL_PREFIX` поведінка як зараз.
- `STATIC_URL`, `SESSION_COOKIE_PATH`, `CSRF_COOKIE_PATH` з урахуванням префікса;
  `CSRF_TRUSTED_ORIGINS` з env (для POST через HTTPS у Caddy).
- Перенаправлення старих адрес без префікса на `/mechanic/...`.
- Caddy має передавати запити **без обрізання префікса** (`handle /mechanic*`, не `handle_path`).
- Відкриті питання до користувача: значення `DEBUG` на сервері; чи потрібні
  редиректи старих адрес чи 404.

## 10. Як писати промти для агента

Агент найкраще працює, коли промт містить:
1. **Мету** — що має змінитися для користувача (а не які рядки правити).
2. **Межі** — що чіпати не можна (БД/моделі/міграції, Caddy, сервер, бізнес-логіка).
3. **Режим** — «спочатку проаналізуй і запропонуй» або «реалізуй одразу».
4. **Критерії перевірки** — що агент має перевірити перед звітом.
5. **Чи робити commit/push** — за замовчуванням агент не комітить без дозволу.

Важливо врахувати:
- Зміна моделей → нова міграція → на сервері обов'язково `migrate` і бекап БД.
- На сервері реальні дані: міграції мають бути безпечні для наявних записів.
- Сервер на `runserver` без автоперезапуску після ребуту.
- Агент не має доступу до сервера — команди на сервері виконує користувач
  і вставляє вивід у чат.

Шаблон:
```
## Завдання: <коротко>
Контекст: <навіщо, що болить>
Що потрібно: <очікувана поведінка>
Обмеження: <що не змінювати>
Режим: спочатку аналіз і пропозиція / реалізуй одразу
Перевірки: <сценарії>
Git: не комітити / закомітити / закомітити і запушити
```
