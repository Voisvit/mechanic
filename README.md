# Журнал технічного обслуговування обладнання

Вебзастосунок на Django для обліку обладнання, планування технічного обслуговування, ведення журналу виконаних робіт, обліку запчастин і перегляду місячних та річних графіків.

## Призначення

Система орієнтована на виробничу дільницю, де потрібно:

- вести перелік обладнання;
- зберігати технічні характеристики та склад запчастин;
- формувати планові роботи на місяць і рік;
- фіксувати виконані роботи;
- відстежувати прострочені та виконані плани;
- переглядати архів за роками та місяцями;
- друкувати графіки, справу машини та перелік запчастин.

## Технології

- Python 3.11+
- Django 5.2
- SQLite
- Django Templates
- Bootstrap 5 через CDN

## Основний функціонал

### Авторизація

- вхід через стандартну Django authentication system;
- доступ до всіх сторінок лише після входу;
- вихід із системи через кнопку `Вийти`;
- користувачі створюються через Django Admin.

### Обладнання

- список активних машин;
- пошук за назвою та інвентарним номером;
- сторінка `Справа машини`;
- сторінка `ТТХ машини`;
- додавання, редагування, деактивація та відновлення машин;
- окремий список неактивних машин.

### Журнал виконаних робіт

- додавання записів по машині;
- редагування та видалення записів;
- вибір відповідальної особи та виконавця лише з активних осіб;
- прив'язка фактичного виконання до планової роботи;
- автоматичне переведення плану в статус `Виконано` після створення факту виконання.

### Планові роботи та графіки

- головна сторінка показує місячний план-графік;
- вибір місяця та року через GET-параметри;
- місячний графік з динамічною кількістю днів;
- річний графік ППР;
- CRUD для `MaintenancePlan`;
- фільтрація за місяцем, роком, машиною та видом ТО;
- статуси `Заплановано`, `Виконано`, `Прострочено`, `Скасовано`;
- архів графіків без дублювання даних в окремих таблицях.

### Запчастини

- прив'язка запчастин до конкретної машини;
- загальний перелік запчастин з підсумком кількості;
- фільтр за назвою запчастини та машиною;
- посилання на ТТХ машин.

### Довідники

- список дійових осіб;
- додавання, редагування, деактивація та відновлення;
- посади через фіксований перелік значень.

### Друковані форми

- місячний графік;
- річний графік;
- справа машини;
- загальний перелік запчастин.

## Структура даних

У застосунку реалізовані основні моделі:

- `Machine` — обладнання;
- `Person` — дійові особи;
- `Part` — запчастини;
- `MachinePart` — склад запчастин машини;
- `MaintenanceType` — типи ТО та ремонтів;
- `MaintenancePlan` — планові роботи;
- `MaintenanceLog` — фактичні виконані роботи;
- `MachineSpec` — технічні характеристики та описи ЩЗТО / ТО-1 / ТО-2 / ТО-3.

Для `Machine` і `Person` використовується м'яка деактивація через `is_active`, а не фізичне видалення з користувацького інтерфейсу.

## Локальний запуск

### 1. Створити віртуальне середовище

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 2. Встановити залежності

```bash
pip install -r requirements.txt
```

### 3. Підготувати змінні оточення

Скопіюйте приклад конфігурації:

```bash
cp .env.example .env
```

Далі задайте власні значення для:

- `SECRET_KEY`
- `DEBUG`
- `ALLOWED_HOSTS`
- `PORT`

Якщо ви не використовуєте завантаження `.env` через shell або process manager, ці змінні потрібно експортувати вручну перед запуском.

### 4. Застосувати міграції

```bash
python manage.py migrate
```

### 5. Створити суперкористувача

```bash
python manage.py createsuperuser
```

### 6. Запустити сервер

```bash
python manage.py runserver 0.0.0.0:8001
```

Після запуску:

- застосунок: `http://127.0.0.1:8001/`
- admin: `http://127.0.0.1:8001/admin/`

## Початкове наповнення

Для першого запуску зручно створити через admin:

1. типи ТО та ремонтів, наприклад: `0`, `ТО-1`, `ТО-2`, `ТО-3`, `КР`, `СР`, `ПР`;
2. кілька машин;
3. кілька осіб;
4. запчастини;
5. планові роботи.

Після цього дані автоматично з'являться у відповідних розділах графіків, справ машин і переліку запчастин.

## Робота з авторизацією

- неавторизований користувач при спробі відкрити будь-яку сторінку застосунку перенаправляється на `/login/`;
- після успішного входу відбувається перенаправлення на головну сторінку;
- вихід виконується через `/logout/`.

## Корисні маршрути

- `/` — головна сторінка, місячний план-графік;
- `/equipment/` — список обладнання;
- `/archive/` — архів;
- `/parts/` — загальний перелік запчастин;
- `/references/` — довідники / дійові особи;
- `/admin/` — Django Admin.

## Перевірка працездатності

Базова перевірка конфігурації:

```bash
python manage.py check
```

## Підготовка до публікації на сервер

У репозиторії вже передбачений `.gitignore` для:

- `db.sqlite3`;
- `.env`;
- віртуального середовища;
- логів;
- кешів;
- локальних робочих файлів.

Перед деплоєм варто додатково:

1. задати власний `SECRET_KEY` через змінні оточення;
2. вимкнути `DEBUG`;
3. налаштувати `ALLOWED_HOSTS`;
4. не копіювати локальний `db.sqlite3` на GitHub;
5. на сервері створити нову базу командою `python manage.py migrate`;
6. замінити SQLite на серверну СУБД, якщо очікується багатокористувацька робота;
7. налаштувати збір і видачу статичних файлів.

## Публічний репозиторій

Перед публікацією у GitHub:

- не додавайте `.env`;
- не додавайте `db.sqlite3`;
- не додавайте локальне віртуальне середовище;
- використовуйте `.env.example` як шаблон без реальних секретів.

## Поточні обмеження

- використовується SQLite, що підходить для локальної роботи та невеликого навантаження;
- окремих автоматичних тестів у репозиторії поки немає;
- для production потрібно задавати `SECRET_KEY`, `DEBUG` та `ALLOWED_HOSTS` через змінні оточення.

## Ліцензія

Використовується у межах внутрішнього проєкту, якщо інше не буде визначено окремо.
